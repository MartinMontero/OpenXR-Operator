# D-14 — Product vision: the non-developer surface is a v1 requirement

**Status:** ANSWERED by the human, 2026-08-10 (chose option A).

**Decision:** The founding purpose of OpenXR Operator is to empower
non-developers to create XR experiences without writing code — the project
exists because of a post by a non-coder asking whether AI could let someone
like them build for VR. v1 therefore MUST ship a natural-language task
surface: the user describes intent in plain language; the agent observes,
plans, and proposes actions as plain-language diffs; nothing executes
without approval. The declarative YAML flow runner is the power-user and
regression layer underneath — never something a user must hand-write.
Successful sessions can be saved as flows automatically; reading YAML is
optional, writing it is never required.

**Consequences:**
- The approval gate is doubly load-bearing: the summary of every mutating
  action must be readable by someone who cannot read code. Raw JSON diffs
  are not an acceptable approval surface for v1.
- Onboarding (the "first five minutes") targets a non-developer: guided
  setup, no hand-edited configuration for the default local path.
- The model/UI waves gain the natural-language surface requirement; the
  orchestrator maps it to tasks in PLAN.md.
- README leads with this vision; engineering detail follows it.
- This relaxes no security gate. It raises the bar on the approval gate's
  presentation layer.
